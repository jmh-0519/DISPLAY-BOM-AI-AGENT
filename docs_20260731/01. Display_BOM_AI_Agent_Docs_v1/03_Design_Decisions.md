# 설계 결정 기록

이 문서는 Architecture Decision Record(ADR) 형식으로 중요한 선택과 이유를 기록한다.

---

## ADR-001: Single Agent를 사용한다

- 상태: 채택
- 날짜: 2026-07-31

### 배경

프로젝트 초기 범위는 BOM 조회, 비교, 검증, 변경 영향 분석이며 하나의 도메인 안에서 여러 Tool을 선택해 실행한다.

### 검토한 대안

- Single Agent
- 역할별 Multi-Agent

### 결정

Single Agent를 사용한다.

### 이유

- 현재 문제 규모에서 Multi-Agent는 관리 복잡도와 호출 비용을 증가시킨다.
- Tool 계약을 잘 설계하면 하나의 Agent로 충분하다.
- 디버깅과 테스트가 단순하다.
- 프로젝트 멘토의 권고와도 일치한다.

### 결과와 한계

- 초기 개발과 운영은 단순해진다.
- Agent의 Tool 수가 매우 많아질 경우 분류 또는 라우팅 개선이 필요할 수 있다.

## ADR-002: LLM과 데이터 사이에 Tool 계층을 둔다

- 상태: 채택
- 날짜: 2026-07-31

### 결정

LLM이 CSV나 DB에 직접 접근하지 않고 Tool을 통해 기능을 요청하도록 한다.

### 이유

- 입력 검증과 권한 검사를 적용할 수 있다.
- 비즈니스 로직을 Python에서 결정적으로 실행할 수 있다.
- Tool 계약을 유지하면 데이터 소스 변경이 쉽다.
- 실행 로그와 테스트가 가능하다.

## ADR-003: Tool Registry와 Tool Executor를 분리한다

- 상태: 채택
- 날짜: 2026-07-31

### 결정

Tool 목록과 메타데이터 관리는 Registry가 담당하고, 실제 실행과 공통 제어는 Executor가 담당한다.

### 이유

- 등록 책임과 실행 책임을 분리한다.
- Tool 수가 늘어날 때 조건문 난립을 방지한다.
- 로깅, 실행 시간, 예외 처리, 권한 검사를 한 곳에서 적용할 수 있다.

## ADR-004: CSV로 시작하고 Oracle로 확장한다

- 상태: 채택
- 날짜: 2026-07-31

### 결정

초기 MVP는 합성 CSV 데이터를 사용한다.

### 이유

- 실제 회사 데이터 사용 위험을 제거한다.
- Agent와 Tool 구조를 빠르게 검증할 수 있다.
- 데이터베이스 연결 문제와 AI 로직 문제를 분리할 수 있다.

### 향후 조건

Oracle 연계 전 Repository 인터페이스와 조회 전용 보안 정책을 검토한다.
