# Architecture Review

## Week 1 초기 리뷰

### 현재 구조

```text
Streamlit 예정
  ↓
Agent 예정
  ↓
Registry / Executor 예정
  ↓
Tool 예정
  ↓
BomService 구현 완료
  ↓
CSV 데이터 구현 완료
```

### 잘된 점

- 실제 회사 데이터를 사용하지 않고 합성 데이터로 시작했다.
- 데이터 조회 로직을 `BomService`로 분리했다.
- CSV 접근 오류를 명시적으로 처리했다.
- Agent 연결 전에 데이터 계층을 독립적으로 검증했다.
- 최종 구조를 고려해 Tool과 Service의 책임을 구분하려 한다.

### 현재 위험

- Tool 공통 인터페이스가 아직 정의되지 않았다.
- DataFrame을 Tool 결과로 그대로 전달할 경우 직렬화 문제가 생길 수 있다.
- 프로젝트 규모에 비해 Registry와 Executor가 과도하게 복잡해질 수 있다.
- CSV 스키마 변화에 대한 검증이 없다.

### 다음 개선

- 최소한의 Tool 계약부터 정의한다.
- Pydantic 입력 모델 적용 여부를 검토한다.
- Tool Result 표준 형식을 정의한다.
- Registry와 Executor는 현재 필요한 기능만 구현한다.
- 테스트를 코드와 함께 추가한다.

### 리뷰 질문

- Tool이 30개가 되어도 이름과 설명만으로 구분 가능한가?
- CSV가 Oracle로 바뀌면 어떤 파일이 변경되는가?
- Agent 없이 Tool을 독립적으로 실행하고 테스트할 수 있는가?
- LLM이 잘못된 인자를 생성하면 어느 계층에서 차단하는가?
