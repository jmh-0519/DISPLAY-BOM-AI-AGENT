# AI Agent 개발 원칙

이 문서는 Display BOM AI Agent의 설계와 구현에서 판단 기준이 되는 프로젝트 헌법이다. 기능 추가나 구조 변경 시 아래 원칙과 일치하는지 검토한다.

## 1. 설계가 코드보다 먼저다

코드를 작성하기 전에 문제, 책임, 입력, 출력, 예외를 정의한다. 완벽한 설계 문서를 요구하는 것이 아니라 구현 전에 최소한의 방향을 명확히 한다.

## 2. 모든 설계 결정에는 이유를 남긴다

Single Agent, Tool Calling, Registry, Service Layer, CSV 우선 적용 등 중요한 선택은 `03_Design_Decisions.md`에 기록한다.

## 3. LLM은 판단하고 Python은 실행한다

LLM은 사용자 의도 분석, Tool 선택, 결과 설명을 담당한다. 수량 계산, 검증 규칙, 권한 검사, DB 처리와 같은 결정적 로직은 Python에서 실행한다.

## 4. LLM을 신뢰 경계 밖에 둔다

LLM이 생성한 Tool 이름과 인자는 검증한 뒤 실행한다. 임의 SQL, 파일 경로, 시스템 명령을 그대로 수행하지 않는다.

## 5. 모든 외부 동작은 Tool로 명시한다

BOM 조회, 자재 검색, 검증, 비교, 변경 영향 분석 등의 기능은 명시적인 Tool 계약으로 제공한다. Agent가 Service나 DB를 직접 호출하지 않게 한다.

## 6. Agent는 Tool 구현을 알지 못한다

Agent는 Tool의 이름, 설명, 입력 스키마, 출력 계약만 이해한다. Tool 내부가 CSV인지 Oracle인지 알 필요가 없어야 한다.

## 7. 각 계층은 하나의 책임을 가진다

- UI: 입력과 결과 표현
- Agent: 의도 파악과 실행 흐름 조정
- Registry: 사용 가능한 Tool 관리
- Executor: 실행, 검증, 로깅, 예외 처리
- Tool: Agent가 사용할 업무 기능 인터페이스
- Service: 업무 데이터 조회와 가공
- Repository/Data Source: 저장소 접근

## 8. 비즈니스 규칙은 결정적으로 구현한다

필수 부품, 단종 자재, 호환성, 수량, 승인 상태 등의 검증은 프롬프트에만 의존하지 않는다. 가능한 규칙은 코드와 데이터로 관리한다.

## 9. 구조화된 입력과 출력을 사용한다

Tool 입력은 명시적인 스키마로 검증한다. Tool 출력도 성공 여부, 데이터, 메시지, 오류 정보를 일관된 형태로 반환한다.

## 10. 실패를 정상 흐름의 일부로 설계한다

제품 미존재, 빈 검색어, 잘못된 Tool 이름, 필수 인자 누락, 파일 누락, API 오류를 예상하고 사용자에게 이해 가능한 메시지를 제공한다.

## 11. 관찰 가능성을 확보한다

Tool 실행 시간, 선택된 Tool, 입력값, 결과 건수, 오류를 기록한다. 단, API 키와 민감한 데이터는 로그에 남기지 않는다.

## 12. 테스트 가능한 구조를 우선한다

UI나 LLM 없이도 Service와 Tool을 독립적으로 테스트할 수 있어야 한다. 동일 입력에 대해 동일한 결과가 필요한 로직은 단위 테스트로 보호한다.

## 13. 확장성은 교체 가능성으로 만든다

미래를 예측해 과도하게 복잡한 구조를 만들지 않는다. 대신 CSV, SQLite, Oracle 같은 데이터 소스를 교체할 때 Agent와 UI가 영향을 적게 받도록 경계를 둔다.

## 14. 보안을 기본값으로 둔다

환경변수로 비밀정보를 관리하고 `.env`를 공유하지 않는다. 실제 회사 데이터는 학습용 프로젝트에 사용하지 않는다. 향후 SQL Tool은 조회 전용, 허용 목록, 파라미터 바인딩 원칙을 따른다.

## 15. 사람에게 근거를 보여준다

Agent 답변은 가능한 경우 제품 ID, 자재 ID, 버전, 상태, 조회 건수와 같은 근거를 포함한다. 데이터가 없으면 추측하지 않고 없다고 답한다.

## 16. 단순하게 시작하고 필요할 때 확장한다

현재 프로젝트는 Single Agent로 시작한다. 문제 규모와 요구가 명확해지기 전에는 Multi-Agent, 복잡한 오케스트레이션, 불필요한 프레임워크를 도입하지 않는다.

## 17. 프레임워크보다 도메인과 계약을 우선한다

LangChain, LangGraph, Responses API 등 기술은 바뀔 수 있다. Tool 계약, 업무 규칙, 데이터 모델, 테스트는 특정 프레임워크에 과도하게 종속되지 않게 한다.

## 18. 문서와 코드는 함께 진화한다

구조나 기능을 바꾸면 관련 문서도 갱신한다. 문서와 실제 코드가 다르면 문서는 신뢰를 잃는다.

## 19. 모든 기능에는 완료 기준이 있다

"구현 완료"는 코드 작성만을 뜻하지 않는다. 정상 동작, 예외 처리, 테스트, 문서 반영까지 완료해야 한다.

## 20. 작동하는 코드보다 이해하고 유지할 수 있는 코드를 만든다

짧고 영리한 코드보다 역할이 분명하고 설명 가능한 코드를 우선한다. 이 프로젝트의 최종 목적은 본인이 다시 사용할 수 있는 지식과 경험을 만드는 것이다.
