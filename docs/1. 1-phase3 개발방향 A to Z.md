3. Phase3 최종 업무 목표
==================================================

Agent가 다음과 같은 자연어 요청을 처리할 수 있어야 합니다.

“A모델의 C자재가 단종되어 변경해야 한다.
변경 가능한 자재를 찾아서 설계변경을 진행해 줘.”

Agent는 다음 전체 Workflow를 수행해야 합니다.

1. 자연어 요청 분석
2. 대상 모델·ASSY·자재 식별
3. 설계변경 사유와 Action 식별
4. 필요한 기준일과 수요수량 결정
5. 현재 BOM 및 영향 범위 분석
6. 대체 후보 탐색
7. Rule과 속성 기반 적합성 평가
8. 공급사 평가
9. 후보별 점수·등급·근거·순위 제시
10. 사용자의 후보 자재와 주 공급사 선택 승인
11. Review BOM 또는 변경 Preview 생성
12. 최종 영향 및 품평 검증
13. 사용자 최종 Apply 승인
14. Transaction 기반 Production BOM 반영
15. 이력·판정근거·승인·적용 결과 저장
16. 사용자에게 결과와 보고서 제공

LLM은 자연어 의도, 대상, 사유, Action과 평가항목을 식별합니다.
LLM이 원가·재고·납기·품질·적합성을 임의로 생성하면 안 됩니다.
실제 판정과 점수는 Service 및 Rule Engine 결과를 사용해야 합니다.

4. 지원해야 하는 설계변경 Action
==================================================

Phase3에서는 다음 Action을 모두 지원하세요.

- REPLACE
- ADD
- DELETE
- QUANTITY_CHANGE

대상 유형은 다음을 모두 지원하세요.

- MATERIAL
- ASSY

하나의 요청에 복수 Action을 포함할 수 있어야 합니다.

예:

- 자재 A 삭제
- 자재 B 추가
- 자재 C를 D로 교체
- 자재 E의 수량 변경

복수 Action은 하나의 Change Request로 관리하고,
최종 Apply 시 하나의 SQLite Transaction으로 처리하세요.

다음 규칙을 반드시 지키세요.

- 하나의 Action이라도 FAIL이면 전체 Apply 차단
- Apply 도중 하나라도 실패하면 전체 Rollback
- 부분 Apply 금지
- FAIL 예외승인 금지
- CONDITIONAL만 사유를 기록하고 예외승인 가능
- 사용자 승인 전 Production BOM 수정 금지

5. 두 단계 사용자 승인
==================================================

승인을 반드시 두 단계로 분리하세요.

1차 승인:
- 추천 후보 자재
- 주 공급사
- 복수 Action별 선택 결과
- CONDITIONAL 예외 사유

2차 승인:
- 최종 Review BOM
- 전체 영향 모델과 ASSY
- Rule 검증 결과
- 최종 변경 내용
- Production BOM Apply

1차 승인만으로 Production BOM을 변경하지 마세요.
2차 명시적 승인이 있어야 Apply Tool을 실행하세요.

승인 상태와 승인 시점, 선택 대상, 예외 사유를 SQLite에 저장하세요.

6. 대체 후보 추천과 순위
==================================================

각 사례별로 후보를 최소 5개 이상 구성하세요.

후보 결과에는 적합 후보 전체를 표시하고 순위를 제공하세요.

각 후보에 다음을 표시하세요.

- 후보 자재 또는 ASSY
- 후보 유형
- 추천 주 공급사
- 최종 상태: PASS/CONDITIONAL/FAIL
- 총점
- 등급
- 순위
- 적용 Rule
- Rule별 점수와 가중치
- 속성 비교 결과
- 원가
- 납기
- 품질등급
- 재고 충족 여부
- 누락 데이터
- 조건부 사유
- 영향 범위

순위 산정 방식:

1. LLM이 설계변경 사유와 평가항목을 식별
2. 해당 사유에 유효한 Rule이 존재하면 모든 관련 Rule 적용
3. Rule별 가중치로 점수 계산
4. 유효한 Rule이 없으면 자재/ASSY 속성정보를 단계별로 비교
5. 필수조건 위반은 FAIL
6. 데이터 누락은 CONDITIONAL
7. PASS 우선, 그다음 CONDITIONAL
8. 동일 상태에서는 총점과 공급 안정성 기준으로 순위 결정

설계변경 사유가 여러 개면 관련 Rule을 모두 적용하세요.
Rule이 없더라도 LLM이 임의 점수를 만들지 않게 하세요.
속성 기반 평가 알고리즘도 Service에서 결정론적으로 계산하세요.

7. 공급사 평가
==================================================

하나의 자재를 여러 공급사가 공급할 수 있게 모델링하세요.

공급사 평가는 최소 다음을 포함하세요.

- 공급가격
- 납기
- 품질등급
- 공급 안정성
- 유효기간
- 주 공급사 여부
- 공급 가능 상태

후보 자재와 추천 주 공급사를 함께 제시하세요.
사용자는 자재와 주 공급사를 한 번에 선택·승인해야 합니다.

공급사 정보가 일부 없으면 후보를 삭제하지 말고
CONDITIONAL로 유지하며 누락 항목을 표시하세요.

8. 재고와 수요
==================================================

재고는 다음 계층으로 관리하세요.

- 공장 2개
- 공장별 창고 2개
- 창고별 Location 2개

재고 충분 여부는 다음 두 방식을 지원하세요.

- 생산계획 기준
- 사용자가 입력한 요청수량 기준

자연어 요청에 적용일이나 필요수량이 없으면:

- 기본 기준일 자동 적용
- 해당 기간 생산계획 수요 자동 적용

수요 산정 근거와 재고 충족 여부를 결과에 표시하세요.
재고가 없거나 부족하면 Rule에 따라 FAIL 또는 CONDITIONAL을
명확히 판정하세요.

9. 공용 ASSY 처리
==================================================

공용 ASSY의 BOM을 모델별로 복제하지 마세요.
동일 ASSY는 항상 동일한 BOM 구조를 가져야 합니다.

다음 두 경우를 구분하세요.

A. 대상 모델에서 공용 ASSY 자체를 다른 ASSY로 REPLACE:
- 대상 모델과 새 ASSY의 연결만 교체 가능
- 다른 모델의 기존 ASSY 연결은 유지
- 연결 영향 범위 분석

B. 공용 ASSY 내부의 자재 또는 하위 ASSY를 변경:
- 동일 공용 ASSY를 사용하는 모든 모델에 동일하게 영향
- 영향받는 모델 전체를 조회
- 사용자에게 전체 영향 범위를 고지
- 최종 승인 전까지 적용 금지

공용 ASSY 내부 BOM을 특정 모델만 다르게 만드는 방식은 금지합니다.

- 설계변경 사유

15. LangGraph Agent Workflow
==================================================

Single Agent를 유지하고 상태 기반 Workflow를 확장하세요.

상태에는 최소 다음이 포함되어야 합니다.

- 원본 사용자 요청
- 해석된 요청
- 기준일
- 수요수량/생산계획
- 대상 모델/ASSY/자재
- 복수 Action
- 변경 사유
- 후보 목록
- 후보 평가
- 공급사 평가
- 영향 분석
- 1차 승인 상태
- Preview/Review 상태
- CONDITIONAL 예외 상태
- 최종 승인 상태
- Apply 상태
- 오류
- 다운로드 Artifact

Workflow는 사용자 승인 대기 상태에서 멈췄다가
같은 thread_id로 안전하게 재개돼야 합니다.

필수 상태 전이를 구현하세요.

REQUESTED
→ ANALYZED
→ CANDIDATES_EVALUATED
→ WAITING_CANDIDATE_APPROVAL
→ CANDIDATE_APPROVED
→ PREVIEW_CREATED
→ VALIDATED
→ WAITING_FINAL_APPROVAL
→ FINAL_APPROVED
→ APPLIED

조건부 흐름:

CONDITIONAL
→ ADDITIONAL_DATA_REQUIRED 또는 EXCEPTION_APPROVAL_REQUIRED
→ REVALIDATED
→ 다음 단계

실패 흐름:

FAIL
→ BLOCKED

상태 전이가 올바르지 않으면 Tool 실행을 차단하세요.
