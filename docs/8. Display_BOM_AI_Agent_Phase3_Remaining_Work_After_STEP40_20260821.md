# Display BOM AI Agent – Phase3 STEP40 이후 잔여 개발 계획

작성일: 2026-08-21

## 1. 현재 결론

STEP40의 목적은 Phase3 설계변경 Action Coverage를 완성하는 것이다.
지원 Action은 다음 4종이다.

- REPLACE
- ADD
- DELETE
- QUANTITY_CHANGE

현재 REPLACE는 기존부터 E2E가 안정화되어 있고, STEP40 과정에서 ADD/DELETE/QUANTITY_CHANGE의
Analysis, UI, Request, Preview, Apply 흐름을 보완했다.

다만 **STEP40 전체 완료 선언은 단일 Action 정상화만으로 하지 않는다.**
자연어 한 요청에서 2개 이상의 Action을 처리하는 Multi-Action과 COMMON 영향분석을 실제 Agent/UI E2E로
최종 확인한 뒤 STEP40을 종료한다.

따라서 STEP40-N/N1 적용 후 QUANTITY_CHANGE가 정상 동작하면:

> Single-Action Coverage는 완료.
> STEP40 전체 완료까지는 Multi-Action + COMMON 최종 Acceptance 1단계가 남는다.

## 2. STEP40 완료 기준

### 2.1 Single Action

| Action | 완료 기준 | 상태 |
|---|---|---|
| REPLACE | 자연어 -> Analysis -> 후보 -> 승인 -> Request -> Preview -> Apply -> Report | 완료 |
| ADD | 신규 코드를 몰라도 후보 탐색, 중복 ADD 차단, Apply | 완료 |
| DELETE | 후보 없이 대상/영향 분석 후 Apply | 완료 |
| QUANTITY_CHANGE | 현재 BOM QUANTITY -> 변경 후 QUANTITY 검증 후 Apply | STEP40-N 최종 확인 필요 |

공통 정책:

- 별도 변경사유 입력은 필수 아님.
- 사용자가 EOL/COST/COMMONIZATION 등의 명시적 사유를 말하면 해당 Reason을 사용한다.
- 사유가 없으면 등록된 중립 Reason `USER_REQUEST`를 사용한다.
- 생산계획 기반 수요 계산은 사용하지 않고 BOM `QUANTITY`를 기준으로 한다.
- Analysis 단계에서는 실제 Design Change Request를 생성하지 않는다.
- 사용자의 명시적 설계변경 진행 승인 후에만 Request를 생성한다.

### 2.2 Multi-Action + COMMON

STEP40 종료 전에 다음을 실제 Agent/UI에서 한 번 이상 끝까지 검증한다.

예시:

- ASSY REPLACE + 하위 MATERIAL QUANTITY_CHANGE
- MATERIAL REPLACE + DELETE
- ADD + DELETE

확인 항목:

1. 한 자연어 요청에서 Action을 2건 이상 분리한다.
2. 모든 Action이 하나의 Analysis Session에 유지된다.
3. REPLACE/ADD만 후보를 선택한다.
4. DELETE/QUANTITY_CHANGE는 후보선택 없이 Action 검증한다.
5. 각 Action의 PASS/CONDITIONAL/FAIL을 독립 평가한다.
6. COMMON 대상이면 영향받는 최상위 MODEL을 확인한다.
7. 사용자 승인 후 **하나의 Request**로 변환한다.
8. 하나의 통합 Preview를 생성한다.
9. 최종 승인 후 전체 Action을 Atomic Apply 한다.
10. 한 Action이라도 적용 실패하면 전체 Rollback 한다.
11. 완료 Word 보고서에 전체 Action이 기록된다.

이 Acceptance까지 통과하면 **STEP40 완료**로 선언한다.

# 3. STEP40 이후 필수 작업

## STEP41 – Decision Trace / Learning JSONL

### 목적

Agent가 어떤 입력과 Evidence를 보고 어떤 Tool을 사용했고, 사용자가 무엇을 선택했으며,
최종적으로 어떤 결과가 적용됐는지를 구조화된 데이터로 남긴다.

LLM의 비공개 내부 사고과정을 저장하는 것이 아니라, 시스템에서 관찰 가능한 업무 이벤트를 저장한다.

### 저장 대상

- 사용자 원문
- Intent / PLANT / Target / Action / Reason Resolution
- Planning 결과
- MCP Tool Call / Tool Result
- 후보 전체 및 Ranking
- Rule / Attribute / Supplier / Inventory Evidence
- 사용자 후보 선택/반려
- 추가정보 및 재검증 Before/After
- COMMON 영향 확인
- Request Commit
- Preview
- 후보 승인 / 최종 승인
- Apply / Rollback
- 완료 결과
- 향후 Outcome 데이터

### 추가 개발 방향

1. `analysis_decision_events` 또는 동등한 Decision Trace 저장구조 확정
2. Analysis Session ID -> Request ID 연결 유지
3. Agent/MCP 실행 시 주요 Event 저장
4. 업무 종료 시 Learning Record 구성
5. JSONL Export 확장
6. 민감한 내부 LLM Chain-of-Thought는 저장하지 않고 업무 Evidence만 저장

### 필요성

- Agent 오류 Debugging
- Tool 선택/반복 오류 분석
- Agent Evaluation
- 사용자 선택률/추천 적중률 측정
- 향후 Ranking 개선/Fine-tuning용 Dataset 기반

## STEP42 – 10개 업무 Coverage Final Acceptance

### 목적

Unit/Service 테스트가 아니라 실제 사용자가 쓰는 자연어 -> Agent -> MCP -> Service -> DB -> UI 전체 흐름을
Phase3 대표 업무 유형별로 검증한다.

10개 Scenario는 Runtime 분기 조건이 아니라 **업무 Coverage Category**다.
Agent Runtime은 Scenario ID를 알지 못해야 한다.

### 최종 Coverage

1. EOL
2. 공급중단
3. 납기
4. 원가절감
5. 재고
6. 품질
7. CUSTOMER_SPEC / ADD
8. 환경규제
9. COMMON + DELETE
10. ASSY + QUANTITY_CHANGE / Multi-Action

각 Scenario에서 다음을 확인한다.

- 자연어 이해
- PLANT Resolution
- Target Resolution
- Reason Resolution
- 후보 탐색/평가
- Evidence
- 재검증
- COMMON 영향
- Request 생성 Gate
- Preview
- 최종 승인
- Atomic Apply
- 실제 DB 결과
- 설계변경 이력
- Word 완료보고서 재생성

최종 목표:

- 10 / 10 Scenario PASS
- 전체 pytest PASS
- Business Sample Verify PASS

# 4. Phase3 이후로 미뤄도 되는 개선 항목

아래는 Phase3 완료에 필수는 아니다.

- Rule 관리 UI를 JSON 입력에서 업무형 Form으로 개선
- 30/60/90 Outcome 입력 UX 개선
- Product-wide Scan 결과에서 상세 Analysis 바로가기
- 후보 대량 조회 Filter / Sort
- 설계변경 이력 상세 UI 추가 강화
- Word 보고서 디자인/결재란/문서번호 강화
- 완료 보고서 원본 파일 보관 및 보고서 버전관리

현재 완료보고서는 DB Evidence 기반 재생성 방식만 유지한다.

-> Word 완료보고서
