# Display BOM AI Agent v2.0 개발 시작 방향성

## 1. 현재 기준점

Display BOM AI Agent는 v1.0에서 다음 수준까지 완료된 상태다.

- Single Agent 구조
- LangGraph ReAct 기반 Agent Loop
- MCP Server / Client
- 제품·자재·BOM 조회
- 자연어 Query Normalization
- 설계변경 분석
- Review BOM 생성
- AI 품평
- Human-in-the-loop 승인
- Production E-BOM 반영
- Word / Excel 산출물 생성
- 설계변경·품평 이력 조회
- 251개 자동화 회귀 테스트 통과

v1.0은 **CSV 기반으로 설계변경 Workflow를 End-to-End로 수행할 수 있는 MVP**로 본다.

v2.0의 목표는 기능을 단순히 늘리는 것이 아니라, 현재 MVP를 **관계형 DB·트랜잭션·감사 가능성·설명 가능성·RAG를 갖춘 실무형 AI Agent Architecture로 고도화하는 것**이다.

---

# 2. v2.0 핵심 Architecture 방향

프로젝트의 핵심 구조는 다음 원칙을 유지한다.

```text
Streamlit
    ↓
Single LangGraph Agent
    │
    ├─ Skill
    ├─ Planning / ReAct
    ├─ Memory / State
    └─ Human-in-the-loop
    ↓
MCP Client
    ↓
Display BOM MCP Server
    ↓
Service / Rule Engine
    ↓
Repository
    ↓
SQLite
```

보조 경로는 역할을 명확히 구분한다.

```text
정형 업무 데이터
Agent
 → MCP
 → Service
 → Repository
 → SQLite
```

```text
비정형 업무 지식
Agent
 → MCP search_knowledge
 → RAG Service
 → Vector DB
```

```text
비정형 분석 조회
Agent
 → Read-only Text-to-SQL
 → SQL Validator
 → SQLite Read-only Connection
```

---

# 3. 기술별 역할을 섞지 않는다

## LangGraph

담당:

- Agent Workflow
- State
- Memory
- 조건 분기
- Tool Loop
- Interrupt / Resume
- Human Approval

LangGraph에 실제 BOM 업무 로직을 넣지 않는다.

---

## Azure OpenAI / LLM

담당:

- 사용자 의도 이해
- Planning
- Tool 선택
- 결과 해석
- 자연어 설명

LLM이 다음을 임의 판단하지 않도록 한다.

- Compatibility
- Lifecycle 허용 여부
- 승인 여부
- BOM 적용 가능 여부
- Rule 결과

---

## MCP

담당:

- Agent가 사용할 업무 Capability의 표준 인터페이스

예:

```text
get_bom
search_product
search_material
analyze_design_change
create_review_bom
run_ai_bom_review
apply_reviewed_bom
search_knowledge
```

MCP 안에 Business Logic을 중복 구현하지 않는다.

---

## Service / Rule Engine

담당:

- Domain Logic
- Rule 판정
- 상태 전이
- 변경 검증
- 트랜잭션 경계
- 무결성 검증

결정적인 업무 판단은 이 계층에서 수행한다.

---

## Repository

담당:

- 저장소 기술과 Business Logic 분리
- CRUD
- Transaction용 데이터 접근
- CSV / SQLite 구현 교체 가능성 확보

Service가 SQLite SQL을 직접 다루지 않는 구조를 지향한다.

---

## RAG

담당:

- 업무 규정
- 설계변경 매뉴얼
- 품평 기준
- 과거 사례
- 업무 가이드

제품·자재·BOM의 실제 값은 RAG로 조회하지 않는다.

---

# 4. v2.0 최우선 목표

가장 먼저 해야 할 작업은 **SQLite + Repository 기반 전환**이다.

현재 CSV 기반 Runtime에서는 다음 한계가 있다.

- 관계 무결성
- Transaction
- 동시 처리
- 이력 추적
- Atomic Apply
- SQL 분석
- Audit

따라서 STEP24에서는 기능 추가보다 **Data Architecture 안정화**를 우선한다.

---

# 5. STEP24 개발 원칙

진행 순서는 반드시 다음과 같이 한다.

```text
Schema
  ↓
Initialization / Migration
  ↓
Repository
  ↓
Service 전환
  ↓
Workflow 전환
```

CSV를 한 번에 제거하지 않는다.

초기에는:

```text
CsvRepository
+
SqliteRepository
```

를 병행할 수 있게 한다.

목표는:

```text
UI
Agent
MCP
Service

→ 저장 기술이 CSV인지 SQLite인지 몰라도 동작
```

하도록 만드는 것이다.

---

# 6. SQLite 설계에서 반드시 포함할 것

핵심 Domain Table:

```text
products
materials
bom_items
material_compatibility

design_changes
design_change_items
design_change_checks

review_boms
review_bom_items

bom_reviews
bom_review_checks

workflow_events
generated_reports
production_apply_history
```

각 Table에는 가능한 범위에서 다음을 명확히 정의한다.

- Primary Key
- Foreign Key
- UNIQUE
- NOT NULL
- CHECK
- Status Enum
- Revision
- Timestamp
- 필요한 Index

Application Code만 믿지 않고 DB에서도 기본적인 무결성을 보호한다.

---

# 7. Production BOM 변경은 가장 강하게 보호한다

v2.0에서도 다음 원칙은 절대 유지한다.

```text
AI 판단 완료
≠
Production BOM 적용 완료
```

반드시:

```text
Analyze
 ↓
Review BOM
 ↓
AI Review
 ↓
Preview
 ↓
Human Approval
 ↓
Apply
```

순서를 따른다.

그리고 Apply는 하나의 DB Transaction으로 처리한다.

```text
BEGIN

Production BOM 변경
Apply History 기록
Workflow State 변경
Audit Event 기록

모두 성공
→ COMMIT

하나라도 실패
→ ROLLBACK
```

Text-to-SQL이나 LLM이 직접 Production BOM을 수정하는 경로는 만들지 않는다.

---

# 8. 기존 251개 테스트는 v2.0의 안전망이다

v2.0에서는 기존 기능을 고치면서 기존 테스트를 깨뜨리지 않는 것을 기본 원칙으로 한다.

각 단계마다:

```text
기존 Regression Test
+
신규 기능 Test
```

를 같이 수행한다.

특히 STEP24에서는 다음 테스트가 중요하다.

- CSV와 SQLite 반환 계약 동일성
- Migration 건수 일치
- PK / FK 무결성
- 중복 데이터 차단
- 잘못된 Status 차단
- Apply Rollback
- 승인 없는 Apply 차단
- 중복 Apply 차단
- Streamlit Regression
- Agent E2E Regression

# 10. Text-to-SQL 사용 원칙

Text-to-SQL을 도입할 경우 조회 분석용으로만 사용한다.

허용:

```text
SELECT
WITH
```

금지:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
ATTACH
PRAGMA
```

추가 제약:

- Read-only Connection
- Single Statement
- Schema Allowlist
- Column Allowlist
- LIMIT 강제
- 실행시간 제한
- 최대 결과 행 제한
- SQL Validator
- 생성 SQL UI 표시

설계변경 상태 전이나 BOM 변경에는 Text-to-SQL을 사용하지 않는다.

# 12. Memory 방향

현재 LangGraph의 Conversation Memory가 동작하더라도 InMemory 기반이면 다음 수준으로 본다.

```text
Conversation Memory 1차 구현
```

향후에는 다음을 검토한다.

```text
Persistent Conversation Memory
+
Persistent Workflow State
```

Agent 대화와 업무 State를 구분한다.

예:

```text
Conversation

"그 자재"
"아까 그 모델"
"그 중에서"
```

와

```text
Workflow State

change_id
selected_product
old_material
new_material
review_status
approval_status
apply_status
```

는 성격이 다르다.

# 13. Tool 수 증가를 계속 관찰한다

현재 MCP Tool이 이미 다수 존재하고, v2에서는 더 증가할 가능성이 있다.

Tool이 계속 늘면:

```text
Agent
 → 모든 Tool Definition 전달
```

방식의 Tool 선택 정확도가 떨어질 수 있다.

당장 구조를 바꾸지는 않되 다음을 평가한다.

```text
Tool Selection Accuracy
불필요 Tool 호출
Tool Retry
Token 사용량
응답시간
```

필요 시 후반부에:

```text
Intent
 ↓
Capability 선택
 ↓
Relevant Tool Retrieval
 ↓
LLM
```

구조를 검토한다.

# 16. Legacy Tool 계층 정리

현재 Runtime이:

```text
LangGraph
 → MCP Client
 → MCP Server
```

라면 과거의:

```text
tools/
ToolRegistry
ToolExecutor
BomTool
MaterialTool
ProductTool
```

계층은 실제 Runtime에서 사용되는지 확인한다.

바로 삭제하지 않는다.

먼저:

```text
참조 검색
 ↓
Legacy 여부 확인
 ↓
테스트 MCP 방식으로 대체
 ↓
Deprecate
 ↓
삭제
```

순서로 정리한다.

# 17. v2.0 개발 시 가장 중요한 원칙

Agent의 자율성과 시스템의 안전성을 분리한다.

```text
Agent에게 맡길 것

의도 이해
Planning
Tool 선택
질문 재구성
결과 설명
```

```text
시스템이 강제할 것

Rule
State Transition
Transaction
Permission
Approval
SQL Guardrail
Data Integrity
```

즉:

> LLM에게 자유롭게 생각하게 하되, 중요한 업무 변경과 판정은 시스템이 통제한다.

이 원칙을 v2.0 전체 Architecture의 기준으로 유지한다.

# 18. 바로 시작할 개발 작업

v2.0 첫 개발은 STEP24로 진행한다.

```text
STEP24 SQLite 및 Repository 기반 구축
```

순서는:

```text
1. 현재 CSV 데이터 구조 확인
2. Domain별 PK / FK / 상태값 확정
3. SQLite ERD 작성
4. DDL 작성
5. Repository Protocol 확정
6. Repository Contract Test
7. DB Initialization
8. CSV → SQLite Migration
9. Migration Validation
10. Query Repository SQLite 전환
11. Change / Review Repository 전환
12. Apply Transaction 구현
13. 전체 Regression Test
```

특히 처음부터 CSV Runtime을 삭제하지 않는다.

```text
CSV
→ Baseline / 비교 / 복구용

SQLite
→ 단계적 Runtime 전환
```

으로 진행한다.

# 최종 지향점

Display BOM AI Agent v2.0은 단순히 DB와 RAG를 붙인 챗봇을 목표로 하지 않는다.

최종 목표는:

> **LangGraph 기반 Stateful Single AI Agent가 MCP를 통해 BOM 업무 Capability를 조합하고, Service와 Rule Engine이 결정론적 업무 검증을 수행하며, SQLite Transaction과 Human Approval을 통해 안전하게 설계변경을 처리하고, RAG와 Decision Trace를 통해 모든 판단의 근거를 설명할 수 있는 실무형 BOM AI Agent**

를 구현하는 것이다.

다음 작업은 **STEP24 SQLite + Repository 설계부터 시작한다.**
