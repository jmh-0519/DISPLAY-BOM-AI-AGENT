# Display BOM AI Agent Phase3 개발 현황 및 목표 정리

- 기준일: 2026-08-18
- 기준 상태: STEP30 완료, 전체 회귀 테스트 정상 확인
- 다음 핵심 단계: STEP31 – Analysis Explainability & Follow-up Q&A
- 프로젝트 방향: Single Azure BOM Agent + Display BOM MCP Server + SQLite

---

## 1. 문서 목적

본 문서는 Display BOM AI Agent의 Phase3 개발 방향을 재정리하고, 현재까지 구현된 기능과 남아 있는 핵심 기능을 명확히 구분하기 위한 기준 문서이다.

Phase3의 목표는 단순히 “대체 자재 후보를 검색하는 챗봇”을 만드는 것이 아니다.

최종적으로는 사용자의 자연어 설계변경 요청을 이해하고, 설계변경 업무 맥락을 지속적으로 기억하며, 필요한 Tool을 스스로 선택하고, 분석 근거를 설명하고, 사용자 승인에 따라 실제 BOM 변경 Workflow까지 수행하는 **업무형 AI Agent**를 구현하는 것이 핵심이다.

---

# 2. Phase3 핵심 개발 목표

Phase3에서 가장 중요하게 구현해야 하는 흐름은 다음과 같다.

```text
사용자 자연어 설계변경 요청
        ↓
대상 제품 / 품목 / 변경사유 이해
        ↓
BOM 관계 확인
        ↓
설계변경 Metadata Resolve
        ↓
대체 후보 동적 탐색
        ↓
Rule 또는 속성 기반 적합성 평가
        ↓
재고 / 공급사 / 영향범위 평가
        ↓
후보 비교 및 Ranking
        ↓
사용자 후속질문 대응
        ↓
사용자 후보 선택
        ↓
공용 영향 모델 / Spec 확인
        ↓
사용자 영향범위 승인
        ↓
설계변경 Workflow 시작
        ↓
Preview
        ↓
최종 승인
        ↓
BOM Apply
```

중요한 원칙은 **후보 분석 단계와 설계변경 Workflow 단계를 분리**하는 것이다.

후보를 찾았다고 해서 Workflow가 시작되는 것이 아니다.

사용자가 직접 후보를 선택하고, 공용 영향범위를 확인·승인한 이후에만 실제 설계변경 Workflow가 시작되어야 한다.

# 4. 각 Agent 구성요소의 역할

## 4.1 Planning

Planning은 사용자의 현재 입력이 어떤 업무 행동을 요구하는지 판단한다.

예를 들어 다음 요청들을 서로 구분해야 한다.

```text
"이 자재가 단종됐어. 대체품 찾아줘."
→ 새로운 설계변경 분석

"왜 전부 FAIL이야?"
→ 기존 분석 결과 설명

"LJ94-xxxx와 LJ94-yyyy 중 뭐가 더 좋아?"
→ 후보 비교

"Spec 차이가 가장 적은 후보가 뭐야?"
→ 기존 후보의 Spec 기반 재정렬 / 비교

"이 후보로 할게."
→ 후보 선택

"영향범위 확인했어. 진행해."
→ Workflow 진입

"최종 적용해."
→ Apply 승인
```

Phase3에서는 단순 Tool 선택 수준을 넘어 **업무 상태를 고려한 Planning**이 필요하다.

---

## 4.2 Memory

Phase3의 핵심 기능 중 하나이다.

단순 채팅 History가 아니라 현재 진행 중인 설계변경 분석 내용을 구조화하여 기억해야 한다.

예:

```text
DesignChangeAnalysisContext

PLANT
P01

제품
LTA400HR01-001

대상품목
LJ94-100001

품목유형
ASSY

변경사유
EOL

변경유형
REPLACE

검색후보
24

PASS
0

CONDITIONAL
0

FAIL
24

후보별 평가근거
- Candidate A
  - Specification: FAIL
  - Inventory: CONDITIONAL
  - Supplier: PASS
- Candidate B
  - ...
```

또한 후보별 상세 평가 근거도 유지할 수 있어야 한다.

```text
Candidate Evaluation Detail

Attribute: panel_size
Source: 40IN
Candidate: 50IN
Result: FAIL

Attribute: resolution
Source: FHD
Candidate: UHD
Result: FAIL

Attribute: refresh_rate
Source: 60HZ
Candidate: 60HZ
Result: PASS
```

이 Memory가 있어야 사용자가 다음 턴에 “왜 FAIL이야?”라고 물었을 때 이전 분석과 연결해서 답할 수 있다.

---

## 4.3 Skill

Skill은 설계변경 업무 절차와 업무 규칙을 정의한다.

예:

- 후보가 0건인 경우와 검색 후보는 있으나 모두 FAIL인 경우를 구분한다.
- 기술평가 FAIL은 공급사 평가 PASS로 뒤집을 수 없다.
- PASS 후보는 일반 승인 가능하다.
- CONDITIONAL 후보는 추가 확인 또는 예외승인이 필요하다.
- FAIL 후보는 선택할 수 없다.
- 공용 ASSY 내부 자재가 변경되면 해당 ASSY를 사용하는 전체 모델이 영향을 받는다.
- 공용 ASSY 자체를 특정 제품에서 다른 ASSY로 교체하는 경우 해당 제품 연결만 변경한다.
- 평가 근거가 없으면 LLM이 임의로 추측해서는 안 된다.
- 특정 테스트 품목이나 특정 Scenario에 의존해서 판정해서는 안 된다.

---

## 4.4 Tool

Tool은 실제 업무 데이터를 조회하거나 변경하는 기능이다.

현재 및 향후 주요 Tool의 역할은 다음과 같다.

### 기존 주요 기능

- get_bom
- search_material
- search_product
- 설계변경 Request 생성
- 후보 탐색/평가
- 후보 선택
- Preview
- 최종 Apply
- 품평회
- 보고서 생성

### Phase3 추가 필요 Explainability Tool

- get_design_change_analysis
- get_candidate_evaluation_detail
- compare_design_change_candidates
- get_common_item_impact
- get_spec_difference

Tool은 LLM이 추측하지 않고 DB의 실제 근거를 가져오기 위한 핵심 수단이다.

---

## 4.5 MCP

MCP는 Agent가 BOM 업무 기능을 일관된 인터페이스로 사용할 수 있도록 한다.

현재 방향은 하나의 Display BOM MCP Server 안에서 업무 Capability를 제공하는 것이다.

```text
Display BOM MCP Server

1. BOM / Product / Material 조회
2. 설계변경 분석
3. 설계변경 Apply
4. Review BOM / 품평회
5. 보고서 생성
6. Phase3 평가근거 조회
7. Phase3 후보 비교
8. Phase3 영향범위 분석
```

Agent가 DB에 직접 접근하거나 업무 로직을 직접 구현하지 않고,

```text
Agent
  ↓
MCP
  ↓
Service
  ↓
Repository
  ↓
SQLite
```

경로를 유지한다.

---

## 4.6 ReAct

ReAct는 별도의 데이터 저장 기능이 아니라 Agent의 실행 패턴이다.

예:

```text
사용자:
"왜 이 후보는 FAIL이야?"

Reason
→ 현재 설계변경 분석에 대한 후속질문이다.
→ 해당 후보의 상세 평가근거가 필요하다.

Act
→ get_candidate_evaluation_detail 호출

Observe
→ panel_size 불일치
→ resolution 불일치
→ inventory 부족

Reason
→ 기술 필수조건 2개가 실패했다.

Answer
→ 사용자에게 실제 근거를 설명한다.
```

Phase3에서는 Memory, Planning, Skill, MCP Tool이 제대로 연결되어야 ReAct가 실질적인 Agent 동작으로 완성된다.

# 5. 현재까지 구현된 주요 기능

## 5.1 SQLite 단일 Runtime

CSV Runtime을 제거하고 SQLite 기반 단일 Runtime 구조로 전환 완료.

주요 DB:

```text
data/display_bom.db
data/test_display_bom.db
data/display_bom_step27_seed.db
```

---

## 5.2 BOM 구조

현재 BOM 기본 구조:

```text
FA
 └─ OLB
     └─ CP
         └─ BIN
             └─ LC
                 ├─ CF
                 └─ TFT
```

일반 자재는 FA 및 각 ASSY 하위에 연결 가능하다.

동일 ASSY 하위에 동일 자재가 여러 번 존재할 수 있으며 LOCATION으로 구분한다.

---

## 5.3 PLANT 지원

BOM과 설계변경 기능에 PLANT 개념 반영 완료.

- PLANT별 BOM 조회
- P01/P02 동일 제품 BOM 조회 검증
- 다른 PLANT 데이터 혼입 방지
- 재고 및 생산계획 PLANT 연계

---

## 5.4 ASSY 품목명 표준화

ASSY의 품목명은 다음 공정명만 허용한다.

```text
OLB
CP
BIN
LC
CF
TFT
```

제품 VERSION의 품목명은 FA이다.

`OLB ASSY ALT-1` 같은 테스트용 이름은 제거하였으며 재생성되지 않도록 Schema/Verifier 보호를 추가하였다.

후보 간 차이는 품목명이 아니라 DESCRIPTION과 Spec Attribute로 표현한다.

---

## 5.5 설계변경 Reason Metadata

Runtime Metadata는 SQLite DB 기반으로 관리한다.

주요 테이블:

- change_reason_master
- change_reason_alias
- change_reason_scope
- change_reason_evidence_rules
- change_action_reasons

예:

```text
"단종"
   ↓
Alias Resolve
   ↓
EOL
   ↓
MATERIAL / REPLACE 또는 ASSY / REPLACE 허용여부 확인
```

---

## 5.6 범용 후보 탐색

특정 테스트 자재 또는 특정 Scenario에 의존하지 않는다.

기본 방향:

```text
대상품목
   ↓
기존 승인 대체관계 검색
   +
Master/Attribute 기반 동적 후보 검색
   ↓
Rule 적용 가능 여부 확인
   ↓
Rule 존재
→ Rule 평가

적용 가능한 Rule 없음
→ Attribute 기반 평가
   ↓
PASS / CONDITIONAL / FAIL
```

---

## 5.7 공급사 / 재고 평가

후보에 대해 공급사 및 재고 정보를 함께 평가한다.

주요 평가 요소:

- 공급사
- 단가
- Lead Time
- 품질등급
- 공급사 Score
- 현재 재고
- 생산계획 기준 필요수량
- 재고 부족 여부

단, 공급사 평가 PASS가 기술 적합성 FAIL을 뒤집을 수 없다.

---

## 5.8 후보 분석 UI

STEP29 이후 후보 분석과 Workflow 화면을 분리하였다.

후보 선택 전 표시:

1. 변경 대상 품목
2. 현재 상태
3. 변경사유
4. 검색 후보 수
5. PASS / CONDITIONAL / FAIL
6. 후보 비교표
7. FAIL 후보 별도 표시

후보 선택 전에는 설계변경 Workflow를 표시하지 않는다.

---

## 5.9 후보 선택 / 공용 영향 Gate

사용자가 후보를 선택한 후 공용 여부를 확인한다.

### 단독

```text
후보 선택
→ 다른 모델 영향 없음
→ Workflow 진입
```

### 공용

```text
후보 선택
→ 영향 모델 조회
→ Before / After Spec 비교
→ 사용자 영향범위 승인
→ Workflow 진입
```

공용 ASSY 내부 자재 변경 시 해당 ASSY를 사용하는 전체 모델을 영향 대상으로 판단한다.

# 6. 현재 발견된 핵심 미구현 영역

현재 가장 중요한 미구현 영역은 **분석 결과에 대한 Follow-up Q&A**이다.

현재 예:

```text
사용자:
"왜 대상후보가 없는거야?"

현재 Agent:
→ 기존 후보분석 화면 재표시
```

이는 정상적인 Agent 동작이 아니다.

정상 동작:

```text
Agent:
"후보가 없는 것은 아닙니다.
24개 후보가 검색되었지만 모두 기술 적합성 평가에서 FAIL하여
교체 가능한 후보가 0개입니다."
```

그리고:

```text
사용자:
"SPEC이 FAIL이고 재고평가가 CONDITIONAL인 이유를 알려줘."
```

라고 요청하면 실제 평가근거를 조회하여 설명해야 한다.

# 7. STEP31 – Analysis Explainability & Follow-up Q&A

Phase3에서 매우 중요한 다음 개발 단계이다.

## 7.1 목표

설계변경 분석 후 사용자가 결과에 대해 자유롭게 질문할 수 있어야 한다.

예:

```text
왜 전부 FAIL이야?
왜 이 후보만 CONDITIONAL이야?
재고평가가 CONDITIONAL인 이유는?
A 후보와 B 후보 차이는?
가장 Spec 차이가 적은 후보는?
가장 저렴한 후보는?
납기가 가장 짧은 후보는?
공급사 평가가 PASS인데 왜 최종 FAIL이야?
```

---

## 7.2 Analysis Context Memory

현재 분석 결과를 구조화하여 Memory에 유지한다.

저장 대상:

- Plant
- Product
- Target Item
- Target Type
- Parent
- Reason
- Action
- Candidate List
- Candidate Status
- Candidate Score
- Rule Result
- Attribute Result
- Inventory Result
- Supplier Result
- Evaluation Evidence

---

## 7.3 Planning 강화

사용자의 입력을 최소한 다음으로 분류한다.

```text
NEW_CHANGE_REQUEST
EXPLAIN_ANALYSIS
EXPLAIN_CANDIDATE
COMPARE_CANDIDATES
RANK_CANDIDATES
SELECT_CANDIDATE
IMPACT_CONFIRMATION
WORKFLOW_COMMAND
```

---

## 7.4 평가근거 저장

현재처럼:

```text
specification: FAIL
재고 평가: CONDITIONAL
```

정도로만 저장하지 않는다.

상세 근거:

```text
Specification

panel_size
40IN → 50IN
FAIL

resolution
FHD → UHD
FAIL

refresh_rate
60HZ → 60HZ
PASS
```

재고:

```text
required_quantity
available_quantity
shortage_quantity
warehouse/location
```

공급사:

```text
supplier
unit_price
lead_time
quality_grade
supplier_score
```

---

## 7.5 Explain Tool 추가

예정 MCP Capability:

```text
get_design_change_analysis
get_candidate_evaluation_detail
compare_design_change_candidates
```

Agent가 Memory에 없는 상세 데이터를 Tool로 다시 조회할 수 있도록 한다.

---

## 7.6 Skill 보강

Explain Skill 주요 규칙:

1. 후보 없음과 적합 후보 없음 구분
2. FAIL 질문 시 필수 실패 조건 먼저 설명
3. CONDITIONAL 질문 시 부족한 데이터/조건 설명
4. 공급사 PASS는 기술 FAIL을 뒤집지 않음
5. 평가근거가 없으면 추측 금지
6. 후보 비교 시 동일 항목 기준으로 비교
7. 사용자에게 내부 ID나 JSON 구조를 노출하지 않음

# 8. Phase3 완료 시 기대되는 Agent 대화

```text
사용자:
이 자재가 단종됐어. 대체품 찾아줘.

Agent:
→ 대상/사유 식별
→ 후보 탐색
→ 평가
→ 후보 비교표 제공

사용자:
왜 전부 FAIL이야?

Agent:
→ 이전 Analysis Memory 확인
→ 평가근거 Tool 호출
→ 주요 실패 Spec 설명

사용자:
그럼 가장 비슷한 후보는?

Agent:
→ Candidate Compare
→ 가장 근접한 후보와 차이 설명

사용자:
그 후보로 할게.

Agent:
→ 공용 여부 확인
→ 영향 모델/Spec 표시

사용자:
영향범위 확인했어. 진행해.

Agent:
→ 설계변경 Workflow 시작
→ Preview

사용자:
최종 적용해.

Agent:
→ 최종 승인 확인
→ BOM Apply
→ Workflow 이력 저장
→ 보고서 생성
```

이 흐름이 Phase3의 최종 목표이다.

# 11. 개발 원칙

Phase3 개발 시 다음 원칙을 유지한다.

### 1. 특정 테스트 코드에 의존하지 않는다.

```text
특정 Product Code
특정 Material Code
특정 ASSY Code
특정 SCN-xx
```

를 Runtime 로직 분기조건으로 사용하지 않는다.

### 2. 테스트 데이터는 검증용일 뿐 기능 실행조건이 아니다.

### 3. 후보는 동적으로 탐색한다.

### 4. Rule이 없으면 Attribute 기반 평가로 전환한다.

### 5. 데이터 부족은 무조건 FAIL이 아니라 CONDITIONAL로 처리할 수 있다.

### 6. LLM은 DB 사실을 추측하지 않는다.

### 7. 업무 데이터 접근은 MCP Tool을 경유한다.

### 8. Apply는 반드시 사용자 승인 이후 수행한다.

### 9. 공용 BOM 변경은 영향범위를 먼저 설명하고 추가 승인받는다.

### 10. 사용자의 후속질문은 새로운 요청으로 초기화하지 않고 현재 업무 Context에서 이어서 처리한다.

# 12. Phase3 성공 기준

Phase3가 완료되었다고 판단하려면 단순히 후보를 검색하거나 BOM을 변경할 수 있는 수준을 넘어 다음 조건을 만족해야 한다.

1. 임의의 제품/자재/ASSY에 대해 동일한 설계변경 분석 흐름이 동작한다.
2. 사용자의 자연어 변경사유를 Metadata로 해석한다.
3. 후보를 동적으로 탐색한다.
4. 적합성 평가의 근거를 설명할 수 있다.
5. 사용자가 “왜?”라고 물었을 때 이전 분석을 기억하고 답한다.
6. 후보 간 차이를 비교할 수 있다.
7. 공용 BOM 영향범위를 설명할 수 있다.
8. 사용자 후보 선택 전에는 Workflow가 시작되지 않는다.
9. 공용 영향 승인 전에는 Workflow가 시작되지 않는다.
10. 최종 Apply 전 명시적인 사용자 승인을 받는다.
11. 변경 결과와 Audit Trail을 저장한다.
12. 특정 테스트 데이터에 의존하지 않는다.

# 13. 현재 결론

STEP30까지의 개발을 통해 Phase3의 데이터 기반과 설계변경 분석 기반은 상당 부분 구현되었다.

그러나 현재 BOM Agent는 아직 완전한 업무형 Agent라고 보기는 어렵다.

가장 중요한 다음 단계는:

> **분석 결과를 Memory로 유지하고, 사용자의 후속질문을 Planning하여, MCP Tool에서 실제 근거를 조회하고, Skill 규칙에 따라 설명하는 기능**

이다.

따라서 STEP31은 단순한 부가기능이 아니라 **Phase3의 Agentic Core를 완성하는 핵심 단계**로 정의한다.

STEP31 이후부터 BOM Agent는 단순한 Tool 실행형 챗봇이 아니라,

> **업무 맥락을 기억하고, 판단하고, 근거를 확인하고, 사용자와 설계변경 업무를 이어가는 AI Agent**

로 발전하는 것을 목표로 한다.
