# 2. Phase1 → Phase2 → Phase3 연속성

## 2.1 Phase1 v1.0.0

Phase1은 CSV 기반의 1차 MVP였다.

핵심:

- Single LangGraph Agent
- BOM Skill
- Planning / Tool Calling
- Conversation Memory
- Human-in-the-loop
- MCP 기반 업무 Capability
- REPLACE 중심 설계변경
- Review BOM / AI 품평
- 사용자 최종 승인 후 Production E-BOM 반영

Phase1에서 중요한 원칙은 이미 다음과 같았다.

> AI 분석이 완료되었다고 Production BOM을 바로 변경하지 않는다.  
> 업무 검증과 사용자 승인을 거쳐야 한다.

---

## 2.2 Phase2 v2.0.0

Phase2는 Phase1의 Agent/MCP/Service 계약을 유지하면서 Runtime 저장소를 SQLite로 통일했다.

```text
Streamlit
  → Single LangGraph Agent
  → MCP Client
  → Display BOM MCP Server
  → Domain Services
  → SQLite Repositories
  → data/display_bom.db
```

주요 완료사항:

- CSV Runtime 완전 제거
- SQLite Single Runtime
- BOM / 설계변경 / Review / 품평 / 보고서 / Apply SQLite 전환
- Transaction 기반 Production Apply
- Apply 실패 시 Rollback
- 설계변경·품평·적용 이력
- Agent와 Streamlit의 MCP 경로 통일
- RAG / Text-to-SQL 미적용 유지

Phase2까지는 **안전하게 읽고, 검증하고, 승인 후 적용하는 기반**을 완성하는 단계였다.

# 3. Phase3 최종 목표

Phase3의 최종 목표는 단순한 대체품 검색기가 아니다.

> **사용자의 자연어 설계변경 요청을 이해하고, 대상과 사유를 식별하고, 대체 MATERIAL/ASSY를 동적으로 탐색·평가하고, 분석 근거를 설명하며, 업무 Context를 기억한 상태에서 사용자와 후속 대화를 이어가고, 사용자 승인과 시스템 안전장치 아래 Production E-BOM까지 반영하는 실무형 Single AI Agent**

Phase3는 두 개의 기반을 동시에 완성한다.

## 3.1 실무 Workflow 기반

- 자연어 설계변경 요청
- 후보 탐색
- Rule / Attribute 평가
- 원가·납기·재고·품질·공급사 평가
- 공용 BOM 영향 분석
- 사용자 승인
- Atomic Apply / Rollback
- Audit 이력

## 3.2 향후 추론학습 기반

- 자연어 요청
- Agent Planning
- Tool 실행
- 후보 전체
- 평가 근거
- 사용자 질문과 Agent 설명
- 후보 선택/반려
- 승인
- Apply / Rollback
- 사후 성과

를 학습 가능한 이력으로 축적한다.

# 5. 각 구성요소의 역할

## 5.1 Single BOM Agent

담당:

- 사용자 자연어 의도 이해
- 제품 / MATERIAL / ASSY 식별
- 설계변경 사유 식별
- Action 계획
- Tool 선택
- 후속 질문 의도 판단
- 결과와 근거 설명
- 업무 Context를 활용한 중단·재개

Agent는 Production DB를 직접 수정하지 않는다.

---

## 5.2 Planning

Planning은 현재 사용자 입력과 업무 상태를 함께 보고 다음 행동을 결정한다.

최소한 다음 Intent를 구분한다.

```text
NEW_CHANGE_REQUEST
EXPLAIN_ANALYSIS
EXPLAIN_CANDIDATE
COMPARE_CANDIDATES
RANK_CANDIDATES
SELECT_CANDIDATE
IMPACT_CONFIRMATION
WORKFLOW_COMMAND
```

예:

```text
"이 자재가 단종됐어. 대체품 찾아줘."
→ NEW_CHANGE_REQUEST

"왜 전부 FAIL이야?"
→ EXPLAIN_ANALYSIS

"A와 B 중 뭐가 더 좋아?"
→ COMPARE_CANDIDATES

"이 후보로 할게."
→ SELECT_CANDIDATE

"영향범위 확인했어. 진행해."
→ IMPACT_CONFIRMATION / WORKFLOW 진입

"최종 적용해."
→ WORKFLOW_COMMAND
```

---

## 5.3 Memory

Phase3의 Memory는 단순 Chat History가 아니다.

현재 업무 상태를 구조화하여 유지해야 한다.

```text
DesignChangeAnalysisContext

PLANT
Product
Target Item
Target Type
Parent
Action
Primary Reason
Secondary Reasons
Candidate List
Candidate Status
Rule Result
Attribute Result
Inventory Result
Supplier Result
Evaluation Evidence
Selected Candidate
Impact Analysis
Approval State
```

이 Memory가 있어야 다음 턴의:

```text
왜 FAIL이야?
왜 CONDITIONAL이야?
가장 비슷한 후보는?
그 후보로 진행해.
```

를 같은 설계변경 업무 Context에서 처리할 수 있다.

---

## 5.4 Skill

Skill은 BOM 설계변경 업무 절차와 안전 규칙을 정의한다.

핵심 Skill 규칙:

- 후보 0건과 적합 후보 0건을 구분
- `PASS / CONDITIONAL / FAIL` 의미 구분
- FAIL 후보 선택 금지
- CONDITIONAL은 추가 데이터 또는 예외승인 필요
- 공급사 PASS가 기술 적합성 FAIL을 뒤집지 못함
- 공용 ASSY 내부 변경 시 전체 영향 모델 확인
- 공용 ASSY 자체의 모델 연결 교체와 공용 ASSY 내부 BOM 변경을 구분
- 평가 근거가 없으면 추측 금지
- 특정 테스트 코드/시나리오에 의존 금지
- Apply는 명시적 사용자 승인 후에만 수행

---

## 5.5 ReAct

ReAct는 별도의 저장소나 독립 모듈이 아니라 **Single Agent의 실행 패턴**이다.

```text
사용자:
"왜 이 후보는 FAIL이야?"

Reason
→ 현재 분석 결과에 대한 후속 질문

Act
→ 평가 상세 MCP Tool 호출

Observe
→ 실제 Rule / Attribute / 재고 결과 확인

Reason
→ 실패 원인 정리

Answer
→ 사용자에게 업무 용어로 설명
```

업무 데이터 접근과 업무 Capability는 MCP를 통해 수행한다.

```text

  ↓
MCP
  ↓
Service
  ↓
Repository

SQLite
```

Display BOM MCP의 Phase3 Capability는 최종적으로 다음 영역을 지원한다.

1. 제품 / BOM / MATERIAL / ASSY 조회
2. 설계변경 Request 분석
3. 후보 탐색 및 평가
4. 공급사 / 원가 / 납기 / 재고 평가
5. 평가 근거 조회
6. 후보 비교
7. 공용 영향 분석
8. Preview
9. 승인
10. Apply
11. Rule 관리
12. 이력 / 성과 / 학습 데이터 Export

# 6. Phase3 지원 Action

Phase3는 MATERIAL과 ASSEMBLY를 대상으로 다음 Action을 지원한다.

```text
REPLACE
ADD
DELETE
QUANTITY_CHANGE
```

추가 지원 범위:

- 공용 ASSY `QUANTITY_CHANGE`
- 공용 ASSY `REPLACE`
- 한 자연어 요청 안의 복수 Action
- 복수 Action 통합 Preview
- 복수 Action Atomic Apply

복수 변경 중 하나의 필수조건이라도 FAIL이면 전체 Apply를 차단한다.

부분 성공 Apply를 기본 정책으로 사용하지 않는다.

# 7. 설계변경 Reason Metadata 최신 정책

설계변경 Reason Metadata는 SQLite DB에서 관리한다.

주요 테이블:

```text
change_reason_master
change_reason_alias
change_reason_scope
change_reason_evidence_rules
change_action_reasons
```

예:

```text
"단종"
   ↓
Alias Resolve
   ↓
EOL
```

## 7.1 복수 Reason 최신 정책

기존 v3.0 방향성의 **다중 사유 Rule 적용 원칙**과 현재 Metadata 구조를 다음과 같이 통합한다.

한 Action에는 업무 대표값으로:

```text
Primary Reason = 1개
```

를 가진다.

하지만 사용자 요청에서 여러 사유가 식별되면:

```text
Secondary Reasons = 0개 이상
```

을 함께 보존한다.

예:

```text
사용자:
"단종됐고 원가도 높아서 바꾸고 싶어."

Primary Reason
= EOL

Secondary Reason
= COST
```

평가 시에는 **Primary Reason만 사용하는 것이 아니라 식별된 모든 적용 가능한 Reason Rule을 평가**한다.

Rule 충돌 우선순위:

```text
안전 필수조건
→ 변경 사유별 Rule
→ 공통 Rule
→ 최신 유효 Revision
```

Primary Reason은 업무 분류와 대표 사유 기록을 위해 사용하고, Secondary Reason은 평가와 학습 데이터에서 버리지 않는다.

# 8. 후보 탐색 최신 원칙

특정 테스트 Material, ASSY, Product 또는 `SCN-*`에 의존하지 않는다.

후보 탐색 순서:

```text
1. 등록된 승인 대체관계
2. 동일 자재/ASSY 분류 및 핵심 속성 후보
3. 전체 Master의 속성 유사 후보
```

`substitution_relations`는 높은 신뢰도의 후보 Source일 뿐, 후보 탐색의 유일한 Source가 아니다.

## 8.1 Rule 존재

```text
Candidate
→ 적용 가능한 Rule Revision
→ 필수조건 / 평가조건
→ PASS / CONDITIONAL / FAIL
→ 점수 / 등급
```

## 8.2 적용 가능한 Rule 없음

단순히 `RULE_NOT_FOUND`로 종료하지 않는다.

```text
Agent / LLM Planning
→ 변경 사유에 필요한 평가 Attribute Dimension 선택

Service
→ 실제 DB Attribute를 이용해 결정적 비교 / 계산

Data 충분
→ 평가

Data 부족
→ CONDITIONAL
```

LLM은 평가할 관점을 계획할 수 있지만, 실제 값과 결정적 계산을 만들어내지 않는다.

# 9. 상태, 점수, 등급

상태와 점수를 분리한다.

## 상태

```text
PASS
CONDITIONAL
FAIL
```

- PASS: 필수조건 충족
- CONDITIONAL: 추가 데이터 또는 확인 필요
- FAIL: 필수조건 실패

## 점수 / 등급

통과 가능한 후보 간 상대적 적합도 표현.

| 등급 | 점수 |
|---|---:|
| S | 90 이상 |
| A | 80 이상 |
| B | 70 이상 |
| C | 70 미만 |

정렬:

```text
PASS 점수순
→ CONDITIONAL 점수순
→ FAIL은 추천순위 제외
```

FAIL 후보의 실패 Rule과 제외 사유는 숨기지 않는다.

---

# 10. 평가 항목

후보별 평가 범위:

- 기술 / Spec
- Rule
- 원가
- 납기
- 재고
- 생산계획
- 품질
- 공급 안정성
- 규제
- 공급사
- 공용 BOM 영향

공급사 평가와 기술 적합성은 분리한다.

```text
기술 적합성 = FAIL
공급사 평가 = PASS

최종 후보 상태 = FAIL
```

공급사가 우수하다는 이유로 기술 FAIL을 PASS로 변경하지 않는다.

# 11. PLANT / 재고 / 생산계획 최신 기준

Phase3 최초 문서의 샘플 조직은:

```text
공장 2개
공장별 창고 2개
창고별 Location 2개
```

였다.

STEP27 Database Unification 이후 실제 개발 검증 범위는 PLANT 기능을 확장하여:

```text
P01
P02
P03
P04
```

4개 PLANT를 사용하도록 변경하였다.

이는 Runtime 로직을 P01~P04에 하드코딩한다는 의미가 아니다.

원칙:

> **PLANT는 데이터 기반으로 동작하며, 현재 테스트 DB가 4개 PLANT를 포함한다.**

재고는:

```text
PLANT
  → Warehouse
    → Location
      → Item
```

수준으로 관리한다.

수요 기준:

1. 사용자가 요청수량을 명시하면 요청수량 우선
2. 요청수량이 없으면 최신 유효 생산계획 사용
3. 유효 생산계획도 없으면 수량 관련 판정은 CONDITIONAL
4. 적용한 기본값과 가정은 사용자에게 공개

# 12. BOM / ASSY 최신 데이터 규칙

제품 BOM 계층:

```text
FA
 └─ OLB
     └─ CP
         └─ BIN
             └─ LC
                 ├─ CF
                 └─ TFT
```

일반 자재는 FA 및 모든 ASSY에 연결 가능하다.

동일 ASSY 하위의 동일 품목 중복은 LOCATION으로 구분할 수 있다.

## ASSY 품목명

VERSION:

```text
FA
```

ASSEMBLY:

```text
OLB
CP
BIN
LC
CF
TFT
```

만 허용한다.

`OLB ASSY ALT-*`와 같은 테스트형 이름은 사용하지 않는다.

후보 간 차이는 `DESCRIPTION`과 Spec Attribute로 표현한다.

# 13. 공용 / 단독 BOM 정책

## 13.1 단독 자재

후보 선택 후 다른 모델 영향이 없음을 확인하고 1차 후보 선택 단계를 완료할 수 있다.

## 13.2 공용 자재 / 공용 ASSY 내부 자재

후보 선택 후 즉시 Workflow로 넘어가지 않는다.

```text
후보 선택
→ 공용 여부 확인
→ 영향받는 전체 모델 / 상위 ASSY 탐색
→ 모델별 Before / After Spec
→ 사용자 영향범위 확인
→ 1차 승인 완료
→ Workflow 시작
```

## 13.3 공용 ASSY 자체를 특정 모델에서 다른 ASSY로 REPLACE

기존 공용 ASSY BOM 자체를 변경하는 것이 아니라 해당 제품의 ASSY 연결을 교체한다.

다른 모델이 사용 중인 기존 공용 ASSY는 변경하지 않는다.

## 13.4 공용 ASSY 내부 BOM 변경

동일 ASSY BOM은 모든 사용 모델에서 동일해야 한다.

공용 ASSY 내부 MATERIAL 또는 구조 변경은 해당 ASSY를 사용하는 전체 모델의 변경으로 처리한다.

모델별 복제 ASSY를 만들어 일부 모델에만 적용하지 않는다.

# 14. 사용자 승인 최신 정책

Phase3의 **2회 Human Approval 원칙을 유지**한다.

다만 공용품의 영향범위 확인은 1차 승인 안의 필수 Gate로 정의한다.

## 분석 단계

```text
후보 분석
→ 후보 비교
→ 사용자 후보 + 주 공급사 선택
```

### DEDICATED

```text
후보 선택
→ 영향 없음 확인
→ 1차 승인 완료
```

### COMMON

```text
후보 선택
→ 영향 모델 / Spec 확인
→ 사용자 영향범위 확인
→ 1차 승인 완료
```

## Workflow 단계

```text
1차 승인 완료
→ Design Change Workflow 시작
→ 통합 Preview
→ 2차 최종 Apply 승인
→ Atomic Apply
```

즉 공용 영향 확인은 별도의 “3차 승인”이 아니라 **1차 후보 선택 승인의 추가 안전 Gate**이다.

FAIL은 승인할 수 없다.

CONDITIONAL은:

```text
추가 데이터
→ 자동 재검증
→ 계속 CONDITIONAL이면 예외승인 사유 입력
→ 예외승인 이력 저장
```

후 진행할 수 있다.

허용:

```text

→ 동일한 EOL / COST / QUALITY 등의 업무 규칙 검증
```

테스트 데이터는 기능 실행조건이 아니라 검증을 위한 Sample Dataset이다.

# 25. Phase3 개발 원칙

1. Single Agent를 유지한다.
2. 업무 기능은 MCP를 경유한다.
3. Runtime 데이터는 SQLite로 통일한다.
4. 특정 테스트 Product / Material / ASSY / Scenario에 의존하지 않는다.
5. 테스트 데이터는 기능 실행조건이 아니다.
6. 후보는 동적으로 탐색한다.
7. Rule이 없으면 Agent가 평가 Dimension을 계획하고 Service가 실제 데이터로 검증한다.
8. LLM은 DB 사실이나 수치를 임의 생성하지 않는다.
9. FAIL은 Apply하지 않는다.
10. CONDITIONAL은 추가정보/재검증/예외승인 절차를 거친다.
11. 사용자 후보 선택 전 Workflow를 시작하지 않는다.
12. 공용 영향 확인 전 1차 승인을 완료하지 않는다.
13. Production Apply는 최종 명시적 승인 이후에만 수행한다.
14. 공용 ASSY BOM 일관성을 깨지 않는다.
15. 복수 Action은 Atomic Transaction으로 처리한다.
16. 평가 결과는 반드시 설명 가능한 Evidence를 남긴다.
17. 사용자의 후속질문은 현재 Analysis Context에서 이어서 처리한다.
18. 성공 사례뿐 아니라 FAIL / 반려 / Rollback도 학습 이력으로 남긴다.
19. RAG / Text-to-SQL은 Phase3 범위에서 제외한다.
20. 테스트 개수보다 업무 시나리오, Tool 순서, 승인 Gate, DB 무결성, 설명 근거의 정확성을 완료 기준으로 본다.
